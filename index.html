项目介绍 Project Introduction

第一阶段的目标不是"做一个比价网站"，而是先回答五个工程可行性问题。 只有这五个问题都有实测答案，后面的 Web UI、告警、预测才有意义。

  1. 01

    能否稳定获取机票价格

    接入真实数据源并跑通全链路，而非使用固定样本或 mock 数据。已实际调用 Kiwi.com 公开 GraphQL 网关与 Ryanair fare-finder 服务。

  2. 02

    能否区分缓存价与实时价

    每次取价都带 source_type / is_cached / is_realtime 标记，缓存数据在架构上被禁止充当核价证据。

  3. 03

    能否保存历史价格

    append-only 数据模型：flight_offer 存行程身份，price_observation 存每一次取价，只增不改、互不覆盖。

  4. 04

    能否对低价候选二次核价

    对发现阶段排序出的 Top-N 候选，用独立实时源逐个重新取价，再比对两侧报价。

  5. 05

    能否证明结果具有基本可信度

    四态判定（DISCOVERED / VERIFIED / HIGH_CONFIDENCE / INVALID_OR_STALE），一致阈值来自配置文件而非硬编码。

当前阶段边界

Phase 1 只做后端、CLI、数据库与验证。按约定不含 Web UI、Dashboard、携程/去哪儿/飞猪抓取、浏览器自动化、Telegram 告警、AI 分析、价格预测与自动购票。

Flight Price Monitoring 监控管道

一条 run 的生命周期是确定的五步。每一步都落库，因此任何结论都能回溯到具体的请求与响应。

  1. 1Discovery生成合法日期组合，向缓存/指示价源批量取价
  2. 2Rank按归一化价格排序，取 Top-N 作为核价候选
  3. 3Verify用独立实时源对候选逐个重新取价
  4. 4Assess比对发现价与实时价，判定可信度状态
  5. 5Store身份去重写入，价格观测追加保留

Provider 隔离

Provider.search() 永不向上抛异常。所有失败被分类为 AuthError / RateLimitError / TransientError / PermanentError，单个源不可用不会中断整条 run，失败原因写入 provider_run 表。

Flexible Dates 灵活日期

机票最低价往往出现在日期区间的边缘。系统把"出发窗口 × 返程窗口"展开成全部合法组合，而不是只查一个固定日期。

合法组合，而非笛卡尔积

组合必须同时满足：落在出发窗口内、落在返程窗口内、行程天数在 min 与 max 之间。

本项目实测 watch：

6 条航线 × 10 出发日 × 10 返程日
→ 名义 600 种，按 7–14 天行程过滤后
→ 372 个合法组合

另有回归守卫：4/24 出发 + 最短 7 天行程，不允许出现 4/25 返程。该用例已被单测锁定。

全部走配置

日期、机场、舱位、人数、候选数量都来自 YAML / JSON，代码中没有任何硬编码。

id: new-zealand-2027
origins:      [PVG, SHA]
destinations: [AKL, CHC, ZQN]
departure: {from: 2027-04-24, to: 2027-05-03}
return:    {from: 2027-05-03, to: 2027-05-12}
trip_days: {min: 7, max: 14}

providers:
  discovery:    [travelpayouts, kiwi_calendar, ryanair]
  verification: [amadeus, kiwi]
  top_n: 20
为什么要生成组合而不是逐日查询

组合生成让"缓存价"与"实时价"能够落到同一个桶里比对。桶的身份是 ORIGIN-DEST | 出发日 | 返程日 | 舱位 | 成人人数——刻意不含中转次数，因此同一行程的缓存报价与实时报价可以被放在一起判断差异。

Price History 价格历史

历史价格是这个项目的地基。如果新一次扫描会覆盖旧价格，那么"价格趋势"根本无从谈起。

身份与观测分离

  • flight_offer 存行程身份，同一行程只出现一次（INSERT OR IGNORE）
  • price_observation 存每一次取价，只增不改
  • 752 条行程身份 ↔ 1444 条价格观测，同一行程被反复观测多次
  • 各 run 的观测互不覆盖：run#1=592 · run#2=472 · run#3=100 · run#4=100 · run#5=33 · run#6=147

Multi-source Verification 多源核价

这是整个项目最有价值的部分。缓存价会骗人，而且骗得很整齐。

四态判定

DISCOVERED

只有发现价，尚未核价。候选的默认状态。

VERIFIED

实时源复现了发现价，差异在阈值内（默认 ≤5%）。

HIGH_CONFIDENCE

≥2 个独立实时源同时给出接近报价。

INVALID_OR_STALE

发现价明显低于所有实时报价，差异超过失效阈值（默认 >15%）。

阈值写在 config/settings.yaml（agreement_threshold_pct: 5.0、stale_threshold_pct: 15.0），不硬编码在逻辑里。跨币种比对使用静态 FX 归一为可比价。

核心发现：缓存价对新西兰 2027 系统性乐观 30–40%

所以这个项目在做什么

如果只做"发现"，那 50 个假低价会被直接推送出去，看起来全是好消息，实际一个都买不到。 第一阶段的验收目标正是拦下它们——50 / 50 全部拦下。同时 VERIFIED 路径被证明可达（6/6，误差 0.0%）：低价一旦为真，系统能确认它。

Low-price Alerts 低价提醒

提醒的价值不在于"发得多"，而在于"发的都是真的"。因此提醒规则由可信度状态直接决定。

可信度状态是否允许通知理由
VERIFIED 通知 已被独立实时源确认，可直接行动
HIGH_CONFIDENCE 通知（最高优先级） ≥2 个独立实时源一致，可信度最高
DISCOVERED 静默 尚未核价，仅作为候选记录
INVALID_OR_STALE 必须静默 已被证伪的假低价，推送即误导

当前进度

数据层已经完全可以支撑这条规则：candidate_verification 表里 57 条判定结果随时可查询。通知通道本身（Telegram / 邮件等）按约定属于后续阶段。

为什么先做核价再做通知

实测数据显示，同一批候选中 87.7%（50/57）在核价后被证伪。先接通知等于先批量制造噪音。顺序反了，这个功能就是负价值。

About 关于项目

一个以"可验证"为前提的机票价格监控后端。Python 3.13 / CLI / SQLite，无 Web 框架，无前端依赖。

技术栈

  • Python 3.13 + argparse CLI
  • SQLite 持久化，schema_version 1
  • PyYAML 为唯一第三方运行时依赖
  • HTTP 层基于标准库 urllib，自带重试与退避
  • 测试 52 项，全部通过

已知限制

  • kiwi / kiwi_calendar 使用 Kiwi.com 公开 GraphQL 网关，属非官方接口，schema 可能变动；适配器做防御式解析，字段变更会在日志与 provider_run 中显式暴露。
  • 两个 Kiwi 适配器是独立数据路径（缓存矩阵 vs 实时搜索），但不是独立厂商。跨厂商核价目前由 ryanair → kiwi 组合证明。
  • FX 为配置文件中的静态汇率，仅用于跨币种可比，不构成汇率系统。
  • kiwi_calendar 价格矩阵单次上限 100 行，372 组合时会触发截断告警。
